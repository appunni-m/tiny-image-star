# Tiny Image Star design-editor parity ledger

Reviewed 2026-10-05 against the current Tiny Image Star source tree and Figma's public design-editor documentation. This is a working acceptance ledger, not a claim of complete parity. The product target is Figma Design's canvas/editor workflow, implemented locally with Pillow-RS/WASM for raster work; the requested saved-recipe batch workflow is the one deliberate extension.

| Raster editing | Original bytes remain local; Pillow-RS WASM renders non-destructive adjustments and full-resolution exports. A worker retains a decoded source only when the full image fits its cache; over-budget previews decode from the unchanged original bytes and release their working copy afterward. The editor also releases offscreen previews first, then least-recently-used nonvisible source and fallback-bitmap resources under its device-tiered memory budget, while protecting visible, selected, active, restoring, and export sources. Edited previews are rebuilt when layers or pages are duplicated; offscreen clones wait until they enter the viewport. MI-GAN runs locally in a one-thread ONNX/WASM worker for brush-based object erase and a basic unprompted Expand operation on the same image layer; source pixels and geometry remain recoverable. The current feature descriptions and detailed technical limits live in the [README](../README.md), [`.fig` import readiness notes](fig-import-readiness.md), and [local workspace and sharing design](local-folder-sharing-design.md). Those documents are the source of truth for the implementation's exact limits; this table highlights product-level gaps.

Figma's current [Effect API](https://developers.figma.com/docs/plugins/api/Effect/) exposes beta progressive blur with a start radius and normalized start/end points. Tiny Image Star now imports and exposes those values for layer and background blur. Canvas rendering uses two to six bounded blur passes blended along that direction; the pass count drops for large surfaces, so this remains an approximation that needs visual comparison against Figma. Progressive foreground blur fails closed in editable SVG export instead of silently becoming a uniform blur; use raster export for that appearance. Browser visual and device testing remains deferred with the wider feature batch.

The Inspector's **Align & distribute** section now exposes **Tidy up** for a clear selected row, column, or rectangular grid. One-dimensional arrangements adjust spacing along their row or column axis while retaining the common gap; grids are anchored from their top-left. It refuses ambiguous or ragged selections, Auto Layout children, locked layers, and moves that would change a position-variable binding. This follows Figma's documented [Tidy up behavior](https://help.figma.com/hc/en-us/articles/360039956914-Adjust-alignment-rotation-position-and-dimensions); compare varied-size grids and the rendered result in the deferred browser workflow before claiming exact interaction parity.

The local luminance-mask implementation follows the SVG 1.1 sRGB luminance-to-alpha coefficients (`0.2125 / 0.7154 / 0.0721`). Figma documents that the luminance of each mask pixel determines opacity, but does not publish the exact coefficients or interpolation setting; pixel-exact Figma matching remains unverified pending reference exports.

Drop shadows now retain Figma's `showShadowBehindNode` option (default `false`) through `.fig` import, the Inspector, and local document validation. Canvas rendering builds a bounded transformed geometry mask and removes shadow pixels inside that geometry unless the option is enabled; if the mask cannot be allocated, the affected shadow is omitted. Editable SVG exports represent drop shadows when **Show behind transparent areas** is enabled. For the default clipped behavior, SVG also supports fully opaque, un-stroked solid rectangles with uniform corners and ellipses using a solid fill, normal blending, no node/fill alpha, and only layer-blur, inner-shadow, and drop-shadow effects; their base paint covers the clipped portion of the shadow, while the supported effect chain remains editable. Alpha-bearing paints and other node types fail closed with a layer-specific diagnostic and raster-export guidance because one SVG filter cannot preserve geometry clipping across all supported node types. Vector PDF now accepts a single `feDropShadow` on one solid-filled rectangle, ellipse, circle, or simple polygon: the blurred shadow uses a bounded alpha-masked image while the source geometry remains a vector path. Opaque fills cover the shadow in their geometry for the default clipped appearance; alpha-bearing fills can reveal it when **Show behind transparent areas** is enabled. Compound filters, strokes, masks, gradient fills, and unsupported geometry still fail closed. The SVG exporter continues to reject clipped shadows on alpha-bearing geometry because its SVG filter output cannot encode that clipping distinction. [Figma's Effect API](https://developers.figma.com/docs/plugins/api/Effect/) defines this flag for transparent and translucent pixels; compare rotated, vector, text, and grouped shapes against Figma before claiming exact parity.

## Verification policy

Node tests and `npm run verify:static` verify local model behavior, worker packaging, and static deployment inputs. They do not prove editor interaction or visual parity. Browser smoke remains deferred until the current feature batch is implemented, as requested; afterward, run the complete browser workflow and focused mobile flows, record failures, and fix them together before release review. Real-device and independent-profile checks remain separate evidence required for mobile persistence, sharing, and performance claims.

The text-on-path distance table is capped at 65,536 samples and is built once per canvas draw, then queried with binary search for each glyph. A local synthetic Node microbenchmark with 400 curved anchors and 156 graphemes measured 28.58–33.18 ms when rebuilding the table per glyph versus 0.23–0.32 ms with one reused table (five paired samples after two warmups; diagnostic only, not a browser or device guarantee).

The current browser Pillow-RS runtime is CPU/SIMD only. At the pinned upstream commit, `pillow-rs/gpu` is not part of the JS crate's WASM features, GPU initialization blocks on asynchronous WebGPU requests, and the native Rust `BatchExecutor` has no JavaScript binding. Enabling the crate feature alone cannot add browser GPU processing. A future path needs an async WASM API and an explicit JS batch binding, then full output parity, device-loss fallback, cancellation, cleanup, and end-to-end device benchmarks. Until those exist, the measured CPU worker pool is the supported path; its Node-thread throughput is not GPU or browser evidence.
