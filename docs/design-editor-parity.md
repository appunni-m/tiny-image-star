# Tiny Image Star design-editor parity ledger

Reviewed 2026-10-04 against the current Tiny Image Star source tree and Figma's public design-editor documentation. This is a working acceptance ledger, not a claim of complete parity. The product target is Figma Design's canvas/editor workflow, implemented locally with Pillow-RS/WASM for raster work; the requested saved-recipe batch workflow is the one deliberate extension.

| Raster editing | Original bytes remain local; Pillow-RS WASM renders non-destructive adjustments and full-resolution exports. A worker retains a decoded source only when the full image fits its cache; over-budget previews decode from the unchanged original bytes and release their working copy afterward. The editor also releases offscreen previews first, then least-recently-used nonvisible source and fallback-bitmap resources under its device-tiered memory budget, while protecting visible, selected, active, restoring, and export sources. Image layers and image fills also support Figma-style Tile repetition at a configurable percentage of the original source dimensions; preview scaling does not change the repeat period, and saved crop data remains available when switching back to Fill or Fit. Edited previews are rebuilt when layers or pages are duplicated; offscreen clones wait until they enter the viewport. MI-GAN runs locally in a one-thread ONNX/WASM worker for brush-based object erase and a basic unprompted Expand operation on the same image layer; source pixels and geometry remain recoverable. MagicTouch Interactive Segmenter v2 runs locally in a bounded CPU/WASM worker for include/exclude/lasso subject isolation; it creates a separate transparent PNG layer and keeps the source untouched. ISNet background removal runs locally in a bounded one-thread WebAssembly worker and replaces the active asset on the same image node while retaining the original asset for Undo and restore. Background removal, expansion, object erase, subject isolation, and resolution boost share one serialized local-model lane. MI-GAN is not prompt-guided and resizes inference around the mask, so expand quality and latency must be measured on real photos and mobile devices before claiming parity. Background removal and isolation are capped at 4,194,304 source pixels; ISNet sources are also limited to 64 MiB. Resolution boost caps sources at 524,288 pixels and 2,048 pixels per edge and outputs at 8,388,608 pixels/64 MiB. Model quality, cold-start latency, batch memory, cancellation/recovery, and low-memory-phone behavior still need the deferred browser workflow and real-device checks. The candidate models and mobile performance gate are documented in [local image enhancement research](local-image-enhancement-research.md). |

## Verification policy

Node tests and `npm run verify:static` verify local model behavior, worker packaging, and static deployment inputs. They do not prove editor interaction or visual parity. Browser smoke remains deferred until the current feature batch is implemented, as requested; afterward, run the complete browser workflow and focused mobile flows, record failures, and fix them together before release review. Real-device and independent-profile checks remain separate evidence required for mobile persistence, sharing, and performance claims.

The text-on-path distance table is capped at 65,536 samples and is built once per canvas draw, then queried with binary search for each glyph. A local synthetic Node microbenchmark with 400 curved anchors and 156 graphemes measured 28.58–33.18 ms when rebuilding the table per glyph versus 0.23–0.32 ms with one reused table (five paired samples after two warmups; diagnostic only, not a browser or device guarantee).

### Real Pillow-RS batch throughput diagnostic

The reproducible [`pillow-batch-wasm-probe.mjs`](../scripts/research/pillow-batch-wasm-probe.mjs) runs the current Pillow-RS WASM render path in Node worker threads, transfers each original PNG to its worker, reuses `DecodedSourceCache`, encodes the same adjusted PNG previews as the app, and compares SHA-256 output hashes across worker counts. On 2026-10-03, Node 24.18.0 on an Apple M3 Pro (12 logical cores) produced:

| Source dimensions | Images | Requested workers | Active workers after shared render-memory admission | Render rate | Render time | Peak process RSS |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 1024 × 768 | 24 | 1 | 1 | 4.38 images/s | 5.48 s | 450 MiB |
| 1024 × 768 | 24 | 2 | 2 | 8.29 images/s | 2.90 s | 591 MiB |
| 1024 × 768 | 24 | 4 | 4 | 15.53 images/s | 1.55 s | 692 MiB |
| 1600 × 1200 | 8 | 1 | 1 | 1.71 images/s | 4.69 s | 443 MiB |
| 1600 × 1200 | 8 | 2 | 2 | 3.10 images/s | 2.58 s | 554 MiB |
| 1600 × 1200 | 8 | 4 | 3 | 4.31 images/s | 1.86 s | 620 MiB |

Every output hash matched across worker counts. Four requested workers improved this host's throughput by 3.55× at 1024 × 768 and 2.52× at 1600 × 1200, where the existing 256 MiB active-render budget admitted three concurrent images. The run includes startup separately from the render-rate interval. Peak RSS includes the Node process, all deterministic source fixtures, WebAssembly instances, and outputs; it is not a browser's incremental-worker memory measurement. Node worker threads do not establish Safari/Chrome worker performance or low-memory-phone safety. Use this as evidence that Pillow work benefits from parallel workers on this host, not as a production throughput promise. The browser-worker and representative-device lifecycle gates remain open.
