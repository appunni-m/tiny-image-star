# Local image enhancement feasibility

Reviewed 2026-10-04 against official model repositories/papers and the official ONNX Runtime Web and LiteRT.js documentation. This document records the candidate review and the remaining release evidence; model integration alone does not establish acceptable phone performance or production readiness.

## Decision

Tiny Image Star now includes an explicit local 4× resolution-boost action and saved-recipe/batch integration using the pinned Real-ESRGAN general x4v3 ONNX conversion. The model is bundled with the deployed app and loaded only when needed; inference stays in a WebAssembly worker. This clears the architecture and bounded-input/output integration gate, not the release gate: full browser workflows, output-quality comparisons, low-memory recovery, and representative Android/iOS performance remain unverified. Do not describe the operation as prompt-guided editing or promise mobile speed. Keep multi-gigabyte diffusion weights out of the default app.

## Runtime and safety constraints

ONNX Runtime Web documents WASM as the CPU provider and recommends it for very small models or environments without a supported GPU. CPU inference should prefer uint8 quantized weights when available; float16 is not native to CPU and may be slow. WASM threading depends on cross-origin isolation. WebGPU can accelerate heavier models on supported browsers, but it cannot be the only path: the current ONNX Runtime browser matrix does not list WebGPU on iOS browsers. These are runtime capabilities, not model-specific latency promises. See [ONNX Runtime Web performance guidance](https://onnxruntime.ai/docs/tutorials/web/performance-diagnosis.html), [deployment guidance](https://onnxruntime.ai/docs/tutorials/web/deploy.html), and [browser support matrix](https://onnxruntime.ai/docs/get-started/with-javascript/web.html).

Upscaling by 4× in each dimension creates 16× as many output pixels. A 1-megapixel input becomes 16 megapixels: an RGBA8 output alone is about 64 MiB, and a three-channel float32 output tensor is about 192 MiB before model activations, source buffers, and the editor's retained previews. Tiling can bound intermediate activations but does not make the final full-resolution image free. Any implementation must therefore have explicit source-pixel, output-pixel, tile, and memory admission limits; serialize model inference within the shared worker budget; support cancellation that drains the worker before releasing buffers; and leave the original asset recoverable.

## Reproducible ONNX/WASM probe

The upstream Real-ESRGAN v0.3.0 release adds the tiny `realesr-general-x4v3` model and warns that its performance may be limited; the model zoo describes it as a general-scene model with weaker deblur and denoise than the larger models. A community ONNX conversion is available from [SkillSafe AI](https://huggingface.co/skillsafe-ai/realesr-general-x4v3); the tested FP32 file was 4,866,428 bytes with SHA-256 `a946f7a9397021b9b6b7e71df3d2821b04cc09ff244423b7ca79cb191ce4a00e`. The official release describes the x4v3 model as small and multi-scale, while the converted model card reports dynamic NCHW input and x4 output. Treat the conversion and its claims as a candidate artifact, not as an upstream release. See the [v0.3.0 release](https://github.com/xinntao/Real-ESRGAN/releases) and [official model zoo](https://github.com/xinntao/Real-ESRGAN/blob/master/docs/model_zoo.md).

The reproducible [single-thread WASM probe](../scripts/research/super-resolution-wasm-probe.mjs) uses the project's pinned `onnxruntime-web` package. Run it with a local model path; it verifies finite outputs, x4 shapes, median inference time after warmup, artifact hash, and process RSS. On 2026-10-02, Node 24.18.0 on macOS arm64, one WASM thread, 32-pixel warmup, and two measured runs per size produced:

| Input | Output | Median inference | Process RSS after run |
| ---: | ---: | ---: | ---: |
| 64 × 64 | 256 × 256 | 217 ms | 211 MiB |
| 128 × 128 | 512 × 512 | 865 ms | 221 MiB |
| 256 × 256 | 1,024 × 1,024 | 3.52 s | 286 MiB |
| 384 × 384 | 1,536 × 1,536 | 7.91 s | 396 MiB |

This is a WASM operator/shape smoke and a CPU sizing warning, not an image-quality, browser, or device benchmark. It excludes decode, tile overlap, alpha restoration, preview replacement, and output encoding. At this single-thread speed, extrapolating from the 256- and 384-pixel runs suggests roughly 54 seconds per megapixel of source on this host; that extrapolation is diagnostic only. The run also increased process RSS from 59 MiB before session creation to 396 MiB after the largest input. The probe is not a performance benchmark for the integrated tiled path, and it is not evidence that large-image or bulk use is acceptable on phones.

## Remaining release gate

1. Compare the pinned ONNX output with the upstream model on deterministic real-photo patches; measure perceptual quality and visible tile seams, not only tensor tolerance.
2. Measure cold and warm startup, peak memory, and end-to-end latency on desktop and representative Android/iOS devices using the deployed browser worker. The current desktop WASM probe is only a CPU sizing warning; it is not a mobile benchmark.
3. Verify cancellation, tab changes, reload, quota failure, undo, recipe retry, and large-batch behavior through the complete browser workflow, then repeat on low-memory phones.
4. Keep the current input/output caps and serialized AI lane until those measurements justify changing them. WebGPU remains an optional experiment and must not replace the CPU/WASM path.

Until this gate passes, describe resolution boost as an available local feature with explicit size limits, not as production-validated mobile performance. A bicubic enlargement may be labeled separately but must not be presented as recovered detail.

## Prompt-guided editing and generation

Figma Design documents text-to-image generation, prompt-based image editing with optional references, and resolution boost in its [image AI workflow](https://help.figma.com/hc/en-us/articles/24004542669463-Generate-and-edit-images-with-Figma-AI). Reviewed **2026-10-04**, the production decision for this project is **NO-GO** for adding prompt-guided generation/editing to the default product under the combined requirements of in-browser, fully local WASM inference, no inference server, redistributable commercial weights, and production mobile memory/latency. FLUX.2 [klein] 4B is a new license/task-fit candidate, but its available mobile conversion misses the size and latency gates and is not a browser-WASM implementation. No candidate below passes every requirement. This is a current feasibility decision, not a claim that such a model can never exist.

### Runtime implications

ONNX Runtime Web's current support table lists WASM CPU execution for Safari/iOS and the desktop/mobile browser matrix; its WebGPU provider is listed only for Chromium desktop and Android, not Safari or iOS Chrome. The WebGPU provider is separately documented as experimental. WebGPU computation remains on-device, but it is **not** the strict WASM-only execution path; it is an optional browser-GPU path with a materially smaller support matrix. See the official [ONNX Runtime Web browser matrix](https://onnxruntime.ai/docs/get-started/with-javascript/web.html) and [WebGPU execution-provider guide](https://onnxruntime.ai/docs/tutorials/web/ep-webgpu.html).

For strict WASM, ONNX Runtime documents a 4 GB address-space ceiling, plus browser-specific `ArrayBuffer` limits near 2 GB. Model weights, activations, input/output tensors, the editor's retained source/preview images, and runtime overhead all compete for that memory. Keeping a model in Cache Storage or IndexedDB avoids repeated downloads but does not reduce its live inference footprint. See [large-model limits](https://onnxruntime.ai/docs/tutorials/web/large-models.html) and [production deployment guidance](https://onnxruntime.ai/docs/tutorials/web/deploy.html). A native iPhone, CUDA, or WebGPU benchmark cannot be used as a proxy for Safari/iOS WASM.

The 2026-10-04 review also checked Google's [LiteRT.js browser runtime](https://github.com/google-ai-edge/LiteRT/blob/main/litert/js/README.md), which supports a WASM/XNNPack CPU path and WebGPU on supported browsers. Its official README warns large models may fail to load because the WASM CPU memory is limited to 2 GB and notes the application must supply model preprocessing and host-loop logic. The [FLUX.2 Klein LiteRT community port](https://huggingface.co/litert-community/FLUX.2-klein-4B-LiteRT) demonstrates chunked graphs on an Android GPU, not a browser WASM pipeline. Even accepting the converter's measurements, its 6.2 GB graph package plus a 778 MB prompt-embedding table and 5-minute 256-pixel phone runs miss this product's download, memory, and latency targets. This is a strong no-go for that artifact; it does not prove a future pruned/distilled model or a separately labeled desktop-WebGPU path impossible.

### Smallest decision benchmark

Do not add a generation/edit UI or bundle model weights until one candidate has (a) an explicit license permitting redistribution and commercial use, (b) a complete self-contained pipeline for both prompt-only generation and image-plus-prompt editing, including prompt/image encoders, tokenizer, denoiser, VAE, and sampler, and (c) a working single-thread or safely threaded WASM build with no server calls. A model that only passes through WebGPU may be considered as a separately labeled optional accelerator, but it does not pass the strict WASM gate and cannot replace the Safari/iOS path.

If a candidate clears those prerequisites, run one fixed 20-case prompt-only + 20-case source-image-edit corpus at 512 × 512 on Safari/WASM on a supported iPhone and Chrome/WASM on a 4 GB-class Android device, with a WebGPU run recorded separately where supported. Record model download bytes, cold initialization, warm median/p95 end-to-end time, peak incremental process memory over the editor baseline, prompt adherence and preservation of untargeted regions via blinded review, and cancellation cleanup. Proposed first-spike acceptance limits are: **≤1 GiB optional model download, ≤512 MiB incremental peak memory, warm p95 ≤30 seconds per 512-pixel result on both WASM phones, zero inference-time network requests, and cancellation that releases model/working buffers while preserving the original image bytes**. These are proposed product gates, not published benchmark results; any failure is a no-go for a production mobile feature. Passing this small gate would justify broader quality, 1024-pixel, reload/offline, and low-memory-device testing; it would not by itself establish production readiness or exact Figma parity.

**Current outcome (2026-10-04):** FLUX.2 Klein 4B shows one Apache-2.0 model can cover both requested tasks and a chunked int8 conversion can run on a midrange Android GPU. It does not clear this product's local-browser-WASM gates: the conversion is multi-gigabyte, its published phone runs take minutes at 256×256, and it has no Safari/WebAssembly evidence. DreamLite remains non-commercial/research-only in its official release. No reviewed model meets commercial redistribution + complete self-contained pipeline + strict browser WASM + production phone memory/latency together. Keep the current local erase, isolate, expand, background-removal, and resolution-boost tools as distinct local features; none is a substitute for prompt-guided editing. Keep generative weights out of the normal deployment until the gate passes.

**Next experiment:** do not port the 6.2 GB FLUX graph package into the app. Wait for a commercially redistributable unified generation/edit checkpoint whose complete prompt tokenizer/encoder, denoiser, VAE, and sampler total ≤1 GiB. When one appears, convert one fixed 256² prompt-only case and one source+prompt edit case to the target WASM runtime first; prove zero inference-time network requests, model-buffer release, and exact source preservation, then run the existing 512² mobile acceptance corpus. This reuses the existing release gate without spending application work on a candidate that misses the download and latency limits by orders of magnitude. The broader parity status remains in the [design-editor parity ledger](design-editor-parity.md).
